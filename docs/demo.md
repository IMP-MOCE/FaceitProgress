# Демо-сценарий защиты

Swagger UI (http://localhost:8000/docs). Кнопка **Authorize**
принимает токен из `/auth/login`. Все игроки вымышленные, данные встроенные демонстрационные
(`FACEIT_API_KEY` не задан).

## Подготовка (до защиты)

```bash
docker compose up --build -d
```

```bash
docker compose exec api python -m app.seed_demo
```

Скрипт создаёт аккаунт `demo@example.com` (пароль указан в `app/seed_demo.py`) с игроком
`demo_player` и целью, «поставленной» 25 матчей назад. Цель помечена `[ДЕМО]`: это
подготовленный пример накопленных матчей, а не эффект тренировок (ПР1, раздел 11).

Откройте вкладку GitHub Actions с последним зелёным прогоном.

## Часть 1. Конвейер (1 мин)

1. GitHub Actions → последний прогон: **Линтеры и типы → Тесты → Сборка образа**.
2. В сводке прогона - таблица: число тестов и покрытие. Артефакт `test-reports` содержит JUnit XML и coverage.xml.

## Часть 2. Основной сценарий (3–4 мин)

| Шаг | Запрос | Что показать |
|---|---|---|
| 1 | `GET /health` | Сервис и БД доступны |
| 2 | `POST /auth/register` - свой email и пароль | 201, пароля и хеша в ответе нет |
| 3 | `POST /auth/login` → **Authorize** | JWT, `expires_in: 1800` |
| 4 | `POST /players` `{"query": "https://www.faceit.com/ru/players/demo_player"}` | 201 по ссылке; `elo`, `synced_at`; `history_complete: false` - у игрока 120 матчей, загружено 100 |
| 5 | `GET /players/1/stats` | Доля побед и K/D с числителем, знаменателем и размером выборки |
| 6 | `GET /players/1/stats?map=de_mirage` | Фильтр по карте; `message`, если матчей меньше 20 |
| 7 | `POST /players` `{"query": "patchy_player"}` → `GET /players/2/stats` | K/D посчитан по 18 матчам из 20: пропуск - не ноль |
| 8 | `POST /goals` `{"player_id": 1, "metric": "win_rate", "action": "Пересмотреть 3 поражения"}` | 201, снимок 20 матчей в `baseline_matches` |
| 9 | Повторить шаг 8 | 409 и `active_goal_id`: активна только одна цель |
| 10 | `GET /goals/{id}/progress` | `collecting`, 0 из 20 - новых матчей ещё нет |

## Часть 3. Защита (2–3 мин)

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | **Logout** в Swagger → `GET /users/me` | 401 и `WWW-Authenticate: Bearer` |
| 2 | Зарегистрировать второго пользователя → **Authorize** его токеном → `GET /goals/1`, `DELETE /players/1` | 404: чужие данные неотличимы от несуществующих (A01, IDOR) |
| 3 | Изменить один символ в токене → любой запрос | 401: подпись не сходится |
| 4 | 6 раз `POST /auth/login` с неверным паролем | Шестой - 429 с `Retry-After` (A07) |
| 5 | `POST /players` `{"query": "https://evil.example/players/x"}` | 422: ссылки только на faceit.com (A10) |
| 6 | `POST /players` `{"query": "source_down"}` и `{"query": "nobody_here"}` | 503 «источник недоступен» отличается от 404 «игрок не найден» (S01) |
| 7 | Показать заголовки любого ответа | `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy` |

## Часть 4. Готовый прогресс цели (1 мин)

1. **Authorize** токеном `demo@example.com`.
2. `GET /goals` → `GET /goals/{id}/progress`: статус `ready`, исходная и новая доля побед,
   `change` в процентных пунктах, оба состава матчей.
3. Повторный запрос возвращает то же сравнение: снимок не меняется при обновлении истории.

## Вопросы, к которым стоит подготовиться

- **Почему 404, а не 403 для чужих данных?** 403 подтверждает, что ресурс существует, и позволяет
  перебирать id. 404 не раскрывает ничего.
- **Почему Argon2id?** Медленный по памяти и времени хеш, рекомендуется OWASP для паролей.
  bcrypt тоже допустим.
- **Где хранится секрет JWT?** В переменной окружения. Без секрета от 32 символов сервис не запустится.
- **Как обеспечена одна активная цель при двух одновременных запросах?** Частичный уникальный
  индекс `WHERE status = 'active'`. Вторая транзакция получает ошибку целостности, и API возвращает 409.
- **Что будет, если FACEIT недоступен?** 503 с `Retry-After`. Сохранённые матчи и `synced_at` не меняются.
- **Почему не сравниваются последние 20 игр, если первые после цели потеряны?** Это подмена выборки,
  и вывод о динамике стал бы неверным (ПР1, раздел 2.2). Сервис честно отвечает `unrecoverable`.
- **Как спецификация соответствует коду?** OpenAPI генерируется из кода. Тест сверяет опубликованный
  `docs/openapi.json` с приложением, а миграцию - с моделями.
